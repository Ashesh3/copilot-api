# Model fallbacks

Open **Dashboard → Fallbacks** to configure an exact source model and its alternate. Fallbacks are disabled until enabled. Rules match the effective model after normal aliases, replacements, redirects, and model variants have been resolved. Choose a target available through an enabled account or a configured custom provider.

An upstream inference **HTTP 422** triggers the alternate model, regardless of the error code or message. Two native JSON results also trigger fallback when the gateway has buffered the response before sending client output: a Messages response with `type: "message"` and `stop_reason: "refusal"`, or a Responses result with `object: "response"`, `status: "incomplete"`, and `incomplete_details.reason: "content_filter"`. Other HTTP statuses, connection errors, exceptions, aborts, and timeouts do not trigger model fallback. Existing transport retries retain their normal behavior.

Rules can form a chain. For example, configure `A → B`, `B → C`, and `C → D` to try `A → B → C → D`. Each arrow requires HTTP 422 or one of the supported buffered refusal results from the preceding model. The chain stops at the first successful response, any other error or unsupported result, a disabled or missing fallback rule, or before returning to a model already tried by that request. Attempts run in sequence, so each additional hop adds the time spent on that model.

The gateway rebuilds endpoint selection for the alternate model and returns the client's original protocol and requested model name. Responses HTTP and WebSocket, conversation compaction, Chat Completions, Anthropic Messages, and Google AI requests use the same policy. Buffered refusal detection depends on the actual upstream endpoint and JSON result, rather than the client's protocol. For example, a Responses request translated into a buffered Messages request can fall back on `stop_reason: "refusal"`. SSE refusal events do not trigger this buffered-response fallback, and a stream that has already produced output cannot be replayed against another model. Custom-provider WebSocket fallbacks buffer the provider's response before emitting the Responses events.

The `/responses/compact` route uses the stored conversation model and follows the same chained fallback policy. It retains the `response.compaction` result shape when an alternate uses Responses, Chat Completions, Messages, or a custom provider.

Before each model switch, model-specific reasoning and signature history is removed before the next request is prepared. This includes Responses reasoning items, Anthropic thinking and redacted thinking blocks, Chat reasoning fields, and Google thought signatures. Ordinary messages and tool calls remain intact. Once a conversation route is stored, later turns go directly to the final successful model and retain its reasoning and signatures. If a client resends the full history, stored hashes exclude only the known old blocks; new blocks from the current fallback model are preserved. A later HTTP 422 or supported buffered refusal can follow that stored model's own fallback rule, applying the same transition filtering for the next model. Raw reasoning is never stored.

Conversation routes are stored permanently in SQLite under a digest derived from the client's authentication credential, explicit thread, conversation, or client session identity, and effective source model. A Codex child thread is separate from its parent's session. Request IDs, prompt cache keys, and message contents do not create a conversation identity. Requests without an identity start from the source and follow its configured chain on each supported trigger. Requests with a stored route start at its successful target and can continue through enabled fallback rules; returning to a model already tried in that request is prevented.

An alternate must return a successful response before its route is stored; a buffered native refusal does not establish a route even when its HTTP status is 200. Streaming responses also require a successful protocol completion; failed or interrupted streams do not establish a route. Only the final successful destination, the traversed route with its per-hop trigger reasons, and hashes of removed old-thinking blocks are retained. Older routes without a recorded reason use `http_422` for compatibility. Routes do not expire or have a configured capacity. Each stored path is checked against the current rules and redirects before reuse; notice changes and unrelated rule changes preserve valid routes. Rules, settings, and conversation routes are included in administrator database downloads.

Two independent notice settings are off by default:

- **Include diagnostic response headers** adds `x-copilot-api-fallback-from`, `x-copilot-api-fallback-to`, `x-copilot-api-fallback-reason`, and the compatibility header `x-copilot-api-fallback-cached` on accepted fallback responses. The reason is `http_422`, `refusal`, or `content_filter` for the triggering upstream result. The last header indicates that a stored conversation route was used; that route retains its original trigger reason. Responses WebSocket lifecycle events carry the same diagnostics in their header metadata.
- **Show native client fallback notice** uses supported client reroute signals. Codex may describe the switch as cybersecurity routing, and Claude Code may describe it as refusal fallback. These are the clients' existing labels even when a different reason caused HTTP 422. Claude Code must advertise its server fallback capability in the request; clients using a custom base URL may not enable that capability. Display depends on the installed client's capabilities and settings.

The authenticated dashboard API is `GET`/`PUT /dashboard/api/fallbacks`; `PUT` takes the full configuration object with `enabled`, `notifyClient`, `nativeClientNotice`, and `rules`. Responses include the configuration revision. The dashboard sends it in `If-Match` when saving so stale edits return HTTP 409 without replacing newer settings. Older documents containing `conversationAffinity`, `affinityTtlSeconds`, or `affinityMaxEntries` are accepted for compatibility, but those fields are discarded and are not returned. Mutations require the existing administrator session and CSRF protections.

## Fallback sources in LLM Debug

LLM Debug shows where evidence of a fallback came from, in both the request list and the detail view:

| Badge | Meaning |
| --- | --- |
| Configured fallback | A gateway rule retried this request after upstream HTTP 422 or a supported buffered refusal. The description identifies the trigger. The compatibility `cached` marker means the conversation used its stored configured route without requiring another refusal or HTTP 422. |
| Upstream fallback | A native Anthropic response explicitly reported a `fallback` block with source and target models. |
| Client retry (inferred) | The next incoming Messages request retried the same content on another model after a completed native refusal. The detail view links to the preceding capture. |
| Fallback requested | The client supplied a `fallbacks` policy. This records the request's intent, including when the provider rejects it; it does not prove that a switch occurred. |

Badges can coexist. For example, a request may include its own fallback policy and also use a configured gateway rule. A gateway-generated native client notice remains a configured fallback; it is added after the upstream capture and is not evidence that the provider performed the switch.

Client retry inference requires the same incoming authentication credential and explicit conversation or child-thread identity, an otherwise identical request body, a different model, and the immediately following logical request within 60 seconds of the refusal. The source and target identify the models requested by the client; a preceding gateway rule or redirect can mean the linked capture used another upstream model. Missing identities, different credentials or child threads, changed content, incomplete responses, and intervening requests prevent the match. This evidence cannot distinguish an automatic harness retry from a manual retry. Observation state is bounded and process-local; clearing or expiring the underlying captures removes pending evidence. Request IDs and shared upstream account credentials do not establish a client identity.

The dashboard's `fallback` object describes configured routing and records its trigger as `http_422`, `refusal`, or `content_filter`. `fallbackObservations` separately records requested policies, explicit upstream blocks, and inferred client retries. These diagnostics do not change routing, retry policy, response bodies, or the retention of debug captures.

Anthropic's beta Messages API supports fields that some compatible providers do not yet accept. Examples include `thinking.display: "updates"`, `fallbacks`, and per-system-message `output_config`. A provider rejecting one of these with HTTP 400 is a compatibility error, not a configured gateway fallback trigger. For native Copilot Messages requests, the exact HTTP 400 `invalid_request_error` message `fallbacks: Extra inputs are not permitted` permits one compatibility retry on the same model with only `fallbacks` removed. The original policy remains available in LLM Debug, but the provider cannot apply that policy on the retry; gateway-configured HTTP 422 rules remain independent. Providers that accept the field receive it unchanged. Other beta-field errors do not use this retry. See the [Anthropic beta Messages contract](https://github.com/anthropics/anthropic-sdk-typescript/blob/135f71e9297683e14614d4307081c0273ed0a09c/src/resources/beta/messages/messages.ts).
