# Storage and admission performance improvements

The user approved starting the improvements identified after PR #122 merged. This work begins at `52f2d17751fa118a0bcf32f120a8fb839c0eba08` and covers SQLite lock acquisition, duplicate admission work, usage aggregation, selective receipt cleanup, and compiled replacement rules.

Keep Bun's built-in SQLite, WAL and `synchronous=FULL`. Replace native five-second lock waiting with asynchronous acquisition bounded by the existing absolute deadline. Never replay a user transaction callback, partial write, or uncertain commit. A writer waiting to begin must not monopolize the shared connection's queue when a WAL reader could proceed. Once BEGIN succeeds, exclusive session ownership lasts through commit or rollback. Tests use a separate process holding a real lock and verify timer progress, continued reads, acquisition after release, timeout cleanup and one callback invocation.

Each HTTP inference admission authenticates and promotes IP trust once. Preserve the two existing guards' public behavior through explicitly admission-scoped reuse or equivalent consolidation, while keeping admin, transparent proxy, worker and custom-auth boundaries intact. Gateway credential resolution should not repeat its digest/inference checks. Reuse a revision freshly read for the current admission when refreshing accounts; no cross-request stale cache or cross-turn WebSocket authority cache. OAuth revocation must be visible on the next turn even when `config_revision` is unchanged. Account deletion, disabling and snapshot consistency remain authoritative.

Usage responses need only the last 24 hours and scalar lifetime totals. The user explicitly rejected retaining seven-day totals. Remove the five-hour/seven-day fields and return `twenty_four_hour` with token/request numbers plus unchanged lifetime and collection metadata. Keep only 24 hours of usage/model and routing detail, including after legacy import/restore. No seven-day rollup table. Preserve minute boundaries, existing future-dated behavior, lifetime first-request timestamp, pending deltas and receipt reconciliation. The dashboard labels the two sections Last 24 hours and Lifetime without fictional quota or reset clocks.

Add a migration providing an index matching history receipt deletion by kind and creation time. Keep old migrations immutable and preserve all non-history receipts and the one-day history replay horizon. Run maintenance on a bounded cadence instead of every telemetry batch, with explicit prune still available and retry after failures. A queue drain should yield between chunks when needed for timer/network progress; keep identical batching/idempotency results.

Compact collection-gap intervals older than 24 hours into fixed lifetime loss numbers and discard the intervals atomically. Clean process runs without remaining references may expire; unclean IDs must remain compatible with paused processes. Expired administrator sessions and temporary setup/device/OAuth codes receive physical cleanup. Active credentials and durable mutation receipts remain intact. Validate archived counters on transfer and retain them in database downloads and logical backups. Collector startup performs the sweep so old data does not wait for the first timer.

Validate replacement rules once for a committed settings value and cache immutable compiled RE2 patterns. Matchers remain private to each text. Resolve the rule set once per payload; preserve ordering, system rule, replacement expansions, error handling, disabled rules, defensive API copies, and request snapshot behavior across concurrent settings edits. Cache identity must distinguish runtimes and test fixtures with equal revisions, and memory must remain bounded or collectible.

No dependency, transport-pooling, retry, diagnostic-capture, attachment, tokenizer, release or production deployment changes are included. The usage UI changes only to expose the selected retention contract. LLM Debug remains outside SQLite. Expired operational records are reviewed separately from active credentials and configuration; preserving active authentication can require persistent identity rows. Verification includes regression red/green, full fresh-process unit tests, typecheck/lint/build, Linux/Bun checks where practical and benchmark comparisons with the audit's reproducible probes.
